# Go Version Upgrade Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Upgrade the repo's Go toolchain (1.16 → 1.26), direct dependencies, CI Action versions, and Docker base images — sub-project B of the repo modernization effort.

**Architecture:** Four independently-verifiable tasks, staged so any breakage is attributable to the task that caused it: (1) Go toolchain + the two legacy build-tag files, (2) dependency version bumps, (3) CI workflow version bumps, (4) Dockerfile base image bumps. No application logic changes — verification is build/vet/test passing against the real pinned toolchain, not new unit tests.

**Tech Stack:** Go 1.26.8 (verified: this exact SDK is already installed locally via `golang.org/dl/go1.26.8`, invoked as the `go1.26.8` command — use it for every verification step in this plan, not the ambient `go`, which is 1.25.7 and not the actual target). Docker is available locally (confirmed: server 29.7.2) for Task 4's verification. `yq` is available for YAML syntax checks in Task 3.

**Spec:** `docs/superpowers/specs/2026-09-11-go-version-upgrade-design.md`

## Global Constraints

- Target Go version is exactly `1.26` in `go.mod`'s `go` directive, and exactly `1.26.8` everywhere a CI workflow or Dockerfile pins a specific patch.
- Use the `go1.26.8` command (already installed) for every build/vet/test verification step in this plan — never the ambient `go` command, which is a different patch version (1.25.7).
- `go test ./...` is expected to still show 2 pre-existing failures (`TestCreateSound`, `TestSay` in `pkg/sound`) on this machine — it lacks `ffmpeg`/`flite`. This is a known, already-documented environmental gap (`.claude/learnings/`), not something to fix here. Confirm via `git diff --stat -- '*.go'` after each task that no application `.go` file changed, so any *new* test failure is attributable to that task.
- Stay on `dgraph-io/badger` v3 (bump to `v3.2103.5`) — do NOT migrate to v4. That's an explicit, separate, out-of-scope decision.
- Do not change `github.com/paynejacob/hotcereal`'s pinned version — no newer tag exists beyond what's already committed, and this plan doesn't touch it unless a task's own build/test step reveals an actual incompatibility (if that happens, stop and report — do not silently pick a different commit).
- This plan only touches `go.mod`, `go.sum`, `cmd/server/server.go`, `cmd/server/development.go`, `.github/workflows/validate.yaml`, `.github/workflows/release.yaml`, and `Dockerfile`. No other file changes, no `web/speakerbob/` changes, no changes to `scripts/build`'s already-documented embed-path bug.

## Self-Review Notes

- **Spec coverage**: every item in the spec's "Scope" section (go.mod bump, build-tag fix, dependency bumps, CI Action bumps, Dockerfile bumps) has a corresponding task. The spec's "Verification approach" section (install go1.26.8, build/vet/test each task, Docker build) is reflected in every task's own verification steps.
- **Placeholder scan**: no "TBD"/"add appropriate X" — every step has the exact command or exact diff.
- **Type/version consistency**: `1.26.8` (Go), `v3.2103.5` (badger), and every Action version are used identically across the spec, this plan's Global Constraints, and each task's steps — no drift between where a version is first stated and where it's later used.
- **Ordering**: Task 1 (toolchain) before Task 2 (dependencies) matters — dependency `go get`/`go mod tidy` behavior can depend on the module's own `go` directive (module graph pruning rules differ pre/post Go 1.17). Tasks 3 and 4 (CI, Docker) have no code dependency on 1-2 and could in principle run in parallel, but are kept sequential here for simplicity and because they touch adjacent concerns (both are "pin the same target version in a different place").

## Post-implementation notes

- Task 1 additionally fixed a `go vet`-flagged unkeyed struct literal in `cmd/server/server.go:58` (adjudicated mid-execution — see the design spec's "Post-implementation notes" for detail).
- `go.mod`'s `go` directive is `1.26.0`, not bare `1.26` as stated in this plan's Global Constraints — forced by `golang.org/x/tools`'s own minimum-version requirement once it was bumped past `v0.1.5` to fix `go generate` (see the design spec's "Post-implementation notes").
- A 5th, unplanned fix was needed after the final whole-branch review: `go generate ./pkg/...` was broken by Go 1.17+ module-graph pruning dropping `hotcereal`'s codegen-tool dependencies from `go.sum`, compounded by that tool's `golang.org/x/tools` floor being too old to run under Go 1.26. Fixed via Go 1.24+ tool-dependency tracking (`go get -tool`) plus bumping `golang.org/x/tools` to `v0.50.0`.
